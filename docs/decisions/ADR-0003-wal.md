### What is WAL and how it works?
WALはDBにおいてデータの整合性を保つために必要である。
例えば挿入データが巨大であったり、変更箇所が多数のページを跨ぐ場合、一度のファイル書き込みで行うことは難しい。
その場合、書き込みの途中でDBがクラッシュすると中途半端なデータの状態となってしまう。WALはそれを防いでくれる。
基本的な動作は以下の通り（このプロジェクトの実装に沿った流れ。詳細は末尾の「Decision」を参照）。

- 変更箇所を特定する（変更後のページ全体と、変わったカタログ全体）
- WALファイル（redoログ）に変更後のイメージを追記し、最後に Commit レコードを追記して fsync する（ここでCommitが確定する）
- 実データ（`pages.dat`、`catalog.json`）を更新する
- クラッシュする
- 次回起動時に、WALを元に Commit 済みの変更を実データへ適用する（Recovery）。Commit されていないレコードは適用せずに捨てる

# WAL / redo / undo / MVCC に関する理解の整理メモ

## 1. 出発点：WALの目的は何か？

最初の疑問は以下だった。

- CRUD 操作中にクラッシュしてもリカバリできることが目的？
- 操作はページ単位で行われるのでは？
- ページ丸ごとログに残す必要がある？
- スロット単位・バイト単位でもログは残せるのでは？

ここから、WALの「粒度」と「主語」が設計の本質であることに気づいていった。

---

## 2. redo / undo / MVCC の混乱と整理

### 当初の誤解
- redo と undo は対になる概念
- redo = やり直し、undo = 取り消し

### 実際の整理
redo と undo は **名前が似ているだけで責務が全く違う**。

| 機構 | 主語 | 目的 |
|---|---|---|
| redo (WAL) | page | クラッシュリカバリ |
| undo | row | 未コミット取消・履歴 |
| MVCC | row | 過去バージョン参照 |

- redo は **物理的な復旧**
- undo は **論理的な履歴**
- MVCC は undo を「参照用データ」として使う仕組み

---

## 3. 「全部 row 単位ログでできるのでは？」という問い

理論的には以下はすべて可能：

- row の before / after を fsync する
- redo / undo / MVCC を 1 本の row ログで実現する

しかし現実には分けた方が合理的。

理由：
- redo は append-only / fsync / 順次 I/O
- undo / MVCC は ランダムアクセス / 参照 / GC 対象
- I/O特性と寿命が真逆

そのため実際のDBは以下の分離をしている：

- redo(WAL)：page単位・永続
- undo/MVCC：row単位・一時的

---

## 4. redo を深掘り：なぜ直接ページを書かないのか？

### 当初の疑問
- 4KB ページをそのまま物理ファイルに書けば良いのでは？
- 4KB なら atomic なのでは？
- redo に書いても結局ページは後で書くのでは？

### 新しく知った概念
- **torn page（部分書き込み）**

---

## 5. torn page の理解

- torn page は DB用語であり、OS/ストレージ現象でもある
- 1回の write / I/O = atomic 永続化ではない
- 前半が新、後半が旧、という状態は普通に起きる
- HDD / SSD ともに atomic ではない

重要な前提：

> **データページは壊れてもよい  
> 正解は WAL にある**

---

## 6. redo がある場合となぜ復旧できるか

redo ログが **ページの after-image（4KB丸ごと）** を持っている場合：

1. redo を fsync（＝正解が確定）
2. OS が後でページを書き戻す
3. 途中でクラッシュ → ページが torn
4. 再起動時、redo を再適用
5. 壊れたページを after-image で踏み潰す

→ ページ構造が壊れていても問題ない

redo がない場合：
- ページ内部が壊れる
- 行境界・slot directory が不明
- 復旧不能

---

## 7. fsync / CRC / append の意味

### fsync
- 「今すぐ書け」ではない
- **「ディスクに到達するまで戻るな」**

### CRC（チェックサム）
- redo ログが途中で壊れても
- どこまで正しいか検出できる

### append（末尾書き）
- 書いた順序 = 時間順
- 途中で壊れても「そこで止まれる」
- fsync が速い
- HDD / SSD と相性が良い

※ 実装との違い：このプロジェクトでは、壊れたレコードで読み込みは止まるが、
  「そこまでの正しい部分で起動を続ける」ことはしない。起動を失敗させる（末尾の「Decision」を参照）。

---

## 8. 4KBページサイズの本当の意味

### 当初の考え
- HDD のセクタが 4KB → atomic なのでは？

### 最終理解
- 4KB は atomic 単位ではない
- OS / FS / ストレージすべてで
  - 自然
  - 揃いやすい
  - 扱いやすい
- **保証ではなく確率論**

正しい整理：

> **4KBページは  
> 安全に書ける単位ではなく  
> 壊れても直せる単位**

---

## 9. undo の本質（最重要の追記）

undo の役割は：

> **「ある時点での row の状態を知ること」**

- undo は「復元手順」ではない
- undo は **過去バージョンそのもの**
- MVCC は undo を辿って参照する

そのため：

- row 内の差分を積み重ねる設計は不利
- 参照時に毎回再構築が必要になる
- **その時点の完全な row を保持する方が合理的**

結論：

> **undo は差分を記録するべきではない  
> undo は“完成形の履歴”であるべき**

---

## 10. 最終的な理解のまとめ

- HDD / SSD は atomic ではない
- alignment は成功率を上げる工夫でしかない
- torn page は必ず起きる前提で設計する
- redo(WAL) は唯一信じられる情報源
- ページは壊れても OK、redo で踏み潰す
- undo / MVCC は row 単位で別管理するのが自然
- undo は差分ではなく、その時点の row を保持する

---

### Decision
Status: 実装済み（`.kiro/specs/wal-implementation/` のステップ1・ステップ2）。
仕様の詳細は同ディレクトリの `design.md` を参照する。ここには、オンディスクの契約に関わる決定と、その理由・制限を記録する。

#### ログの単位
- ページ単位。変更後のページ全体（after-image）を `FullPageWrite` として記録する（FPW方式）
- カタログも全体のイメージを `CatalogWrite` として記録する。`schema` などはページから復元できず、`fs::write` による上書きは torn write で壊れうるため
- SQL単位、スロット単位、バイト列単位は採らない。torn page では行の境界やスロットディレクトリが分からなくなるが、ページ全体のイメージがあれば、構造に関係なく上書きで直せる
- redo専用とし、undoは持たない。SQLがCommit前に失敗した場合は、メモリ上の未Commitの変更（一時マップと作業用カタログ）を捨てるだけで元に戻る

#### WALファイル `wal.log`
`catalog.json`、`pages.dat` と同じディレクトリに置く。append専用。整数はすべてリトルエンディアン。

ヘッダ（17バイト）:

| フィールド | 型 | 内容 |
|---|---|---|
| `lsn` | u64 | レコードごとに+1する通し番号。1から始まる。0は「未適用」を表す予約値で、割り当てない |
| `type` | u8 | 1 = FullPageWrite、2 = CatalogWrite、3 = Commit |
| `len` | u32 | レコード全体のサイズ（ヘッダを含む） |
| `checksum` | u32 | CRC32（多項式 `0xEDB88320`）。`checksum` フィールドを除く、ヘッダとボディ全体が対象 |

ボディ:

| type | ボディ | レコード全体のサイズ |
|---|---|---|
| FullPageWrite | `page_id` u32 + `page_data` 4096バイト | 4117バイト |
| CatalogWrite | `catalog.json` の内容（可変長） | `len` で判別 |
| Commit | なし | 17バイト |

LSNは FullPageWrite、CatalogWrite、Commit のすべてに採番する。起動時は、WALの最後の有効なレコードのLSN+1から再開する（WALが空なら1）。

#### ページヘッダ（28バイト）
`last_applied_lsn`（8バイト）を追加し、ページヘッダを20バイトから28バイトにした。

| オフセット | 型 | フィールド |
|---|---|---|
| 0..4 | u32 | `magic`（`0x50414745`） |
| 4..8 | u32 | `page_id` |
| 8..10 | u16 | `free_space_offset` |
| 10..12 | u16 | `row_count` |
| 12..16 | u32 | `next_page` |
| 16..18 | u16 | `flags` |
| 18..20 | u16 | `_reserved` |
| 20..28 | u64 | `last_applied_lsn`（そのページに最後に適用したWALレコードのLSN。0はWAL未適用） |

- 20バイトヘッダの既存の `pages.dat` とはレイアウトが互換でない。既存のデータファイルは作り直す
- `last_applied_lsn` は、現時点ではRecoveryで参照しない（無条件で書き戻す）。将来の、LSNによるスキップ判定のために予約している

#### Commitの手順
SQLは1つで1トランザクションとする。`commit_changes` の中で、次の順に行う。

1. 一時マップ（変更したページ）と作業用カタログから、変更の一覧を作る。ページは `page_id` 順に1ページ1件、カタログは変わったときだけ1件
2. WALへ、`FullPageWrite`、`CatalogWrite`、最後に `Commit` の順で追記する。`FullPageWrite` のイメージは、ページを複製して、そのレコードに採番するLSNを `last_applied_lsn` に書いたものとする
3. WALを fsync する。ここでCommitが確定する
4. 正式なカタログを、作業用カタログで置き換える
5. `pages.dat` と `catalog.json` を書く。`pages.dat` には、WALと同じバイト列を書く。この2つはCommit時に fsync しない（正解はWALにあるため）
6. 一時マップを破棄する

2〜5のどこかで失敗したら、致命的エラーとして扱う。プロセス内でやり直さず、プロセスを終了して、次回起動時のRecoveryに任せる。メモリ上の状態とディスク上の状態が食い違ったまま、次のSQLを処理しないため。

#### 起動時のRecovery
起動の順序は、ディレクトリ作成 → Recovery → `catalog.json` のロード → `pages.dat` のオープン → WALのオープン。Recoveryは `catalog.json` を読まない。そのため、`catalog.json` が壊れていても、WALに `CatalogWrite` があれば復旧できる。

1. WAL全体を先頭から読んで検査する。壊れたレコードがあれば、何も書かずに失敗する
2. Commit済みの `FullPageWrite` を、LSN順に、無条件で `pages.dat` へ書き戻す。`page_id` がファイルの末尾より先なら、ファイルを延ばす。書き終えたら fsync する
3. Commit済みの `CatalogWrite` の最後の1件を `catalog.json` に書く。書き終えたら fsync する
4. 最後のCommitレコードより後ろ（Commitされていないトランザクションのレコード）を、適用せずに、WALから切り詰めて fsync する。残すと、起動後に追記された新しいトランザクションと連続し、次回のRecoveryがCommitされていないレコードまで1つのトランザクションとして適用してしまう

- 順序を `pages.dat` → `catalog.json` → WALの切り詰めとするのは、先の書き戻しが失敗したときに、WALを手付かずで残して再実行できるようにするため
- `FullPageWrite` はページ全体のイメージなので、同じWALを何度replayしても結果は変わらない（冪等）
- WALがない、または空のときは、何もしない。`catalog.json` と `pages.dat` には触れず、作りもしない
- ページ側の `last_applied_lsn` との比較によるスキップはしない。ページが壊れていると、ヘッダの値も信用できないため

#### 破損したWALの扱い
- 次のいずれかに当たったレコードは、破損として扱う。ヘッダが途中で切れている / `len` が不正 / `type` が不明 / `type` と `len` が合わない / チェックサムが一致しない
- WALの途中の破損と末尾の破損は区別しない。どちらも、Recoveryを失敗させ、起動を失敗させる。プロセスは0以外の終了コードで終了する
- 何も書き戻さず、WALも切り詰めない。調査と手作業での復旧のために、そのままの状態で残す
- `Engine::new` は、`PagedStorage` の起動に失敗しても、メモリストレージにフォールバックしない。フォールバックすると、ユーザーがディスク上のデータの破損に気づかないまま、メモリ上で作業を続けてしまう（CSVストレージのフォールバックは変えていない）

学習メモの「途中で壊れても、そこで止まれる」とは違い、壊れたレコードの手前までで起動を続けることはしない。

制限: 追記の途中でクラッシュして、書きかけのレコードがWALの末尾に残ると、通常のクラッシュでも起動できなくなる。この場合は、WALの末尾を手作業で取り除く必要がある。末尾の書きかけだけを「WALの終端」とみなして続行する方式は、将来の検討事項とする。その場合は、途中の破損との区別が必要になる。

#### 範囲外
- ROLLBACKコマンド、undoログ、MVCC
- WALのコンパクションとチェックポイント。起動のたびにWAL全体をreplayする。Recoveryで切り詰めるのは、Commitされていない末尾だけで、Commit済みのレコードは削除しない
- 1トランザクション内の複数SQL、マルチスレッド、複数プロセスからの同時アクセス
- ページ自体のチェックサムと、`last_applied_lsn` によるスキップ判定
- MemStorage と CsvStorage はWALの対象外。SQLが途中で失敗すると、その時点までの変更が残る（PagedStorage だけが破棄できる）

#### 確認方法
`cargo run -- dump-wal <wal.logのパス>` で、WALのレコード（LSN、type、checksum、OK/NG）を表示できる。
