### What is WAL and how it works?
WALはDBにおいてデータの整合性を保つために必要である。
例えば挿入データが巨大であったり、変更箇所が多数のページを跨ぐ場合、一度のファイル書き込みで行うことは難しい。
その場合、書き込みの途中でDBがクラッシュすると中途半端なデータの状態となってしまう。WALはそれを防いでくれる。
基本的な動作は以下の通り。

- 変更箇所を特定
- relogファイルを先に書く
- 実データを更新
- クラッシュする
- relogファイルを元に変更を適用する

# WAL / redo / undo / MVCC に関する理解の整理メモ

## 1. 出発点：WALの目的は何か？

最初の疑問は以下だった。

- CRUD 操作中にクラッシュしてもリカバリできることが目的？
- 操作はページ単位で行われるのでは？
- ページ丸ごとログに残す必要がある？
- スロット単位・バイト単位でもログは残せるのでは？

ここから、WALの「粒度」と「主語」が設計の本質であることに気づいていった。

---

## 2. redo / undo / MVCC の混乱と整理

### 当初の誤解
- redo と undo は対になる概念
- redo = やり直し、undo = 取り消し

### 実際の整理
redo と undo は **名前が似ているだけで責務が全く違う**。

| 機構 | 主語 | 目的 |
|---|---|---|
| redo (WAL) | page | クラッシュリカバリ |
| undo | row | 未コミット取消・履歴 |
| MVCC | row | 過去バージョン参照 |

- redo は **物理的な復旧**
- undo は **論理的な履歴**
- MVCC は undo を「参照用データ」として使う仕組み

---

## 3. 「全部 row 単位ログでできるのでは？」という問い

理論的には以下はすべて可能：

- row の before / after を fsync する
- redo / undo / MVCC を 1 本の row ログで実現する

しかし現実には分けた方が合理的。

理由：
- redo は append-only / fsync / 順次 I/O
- undo / MVCC は ランダムアクセス / 参照 / GC 対象
- I/O特性と寿命が真逆

そのため実際のDBは以下の分離をしている：

- redo(WAL)：page単位・永続
- undo/MVCC：row単位・一時的

---

## 4. redo を深掘り：なぜ直接ページを書かないのか？

### 当初の疑問
- 4KB ページをそのまま物理ファイルに書けば良いのでは？
- 4KB なら atomic なのでは？
- redo に書いても結局ページは後で書くのでは？

### 新しく知った概念
- **torn page（部分書き込み）**

---

## 5. torn page の理解

- torn page は DB用語であり、OS/ストレージ現象でもある
- 1回の write / I/O = atomic 永続化ではない
- 前半が新、後半が旧、という状態は普通に起きる
- HDD / SSD ともに atomic ではない

重要な前提：

> **データページは壊れてもよい  
> 正解は WAL にある**

---

## 6. redo がある場合となぜ復旧できるか

redo ログが **ページの after-image（4KB丸ごと）** を持っている場合：

1. redo を fsync（＝正解が確定）
2. OS が後でページを書き戻す
3. 途中でクラッシュ → ページが torn
4. 再起動時、redo を再適用
5. 壊れたページを after-image で踏み潰す

→ ページ構造が壊れていても問題ない

redo がない場合：
- ページ内部が壊れる
- 行境界・slot directory が不明
- 復旧不能

---

## 7. fsync / CRC / append の意味

### fsync
- 「今すぐ書け」ではない
- **「ディスクに到達するまで戻るな」**

### CRC（チェックサム）
- redo ログが途中で壊れても
- どこまで正しいか検出できる

### append（末尾書き）
- 書いた順序 = 時間順
- 途中で壊れても「そこで止まれる」
- fsync が速い
- HDD / SSD と相性が良い

---

## 8. 4KBページサイズの本当の意味

### 当初の考え
- HDD のセクタが 4KB → atomic なのでは？

### 最終理解
- 4KB は atomic 単位ではない
- OS / FS / ストレージすべてで
  - 自然
  - 揃いやすい
  - 扱いやすい
- **保証ではなく確率論**

正しい整理：

> **4KBページは  
> 安全に書ける単位ではなく  
> 壊れても直せる単位**

---

## 9. undo の本質（最重要の追記）

undo の役割は：

> **「ある時点での row の状態を知ること」**

- undo は「復元手順」ではない
- undo は **過去バージョンそのもの**
- MVCC は undo を辿って参照する

そのため：

- row 内の差分を積み重ねる設計は不利
- 参照時に毎回再構築が必要になる
- **その時点の完全な row を保持する方が合理的**

結論：

> **undo は差分を記録するべきではない  
> undo は“完成形の履歴”であるべき**

---

## 10. 最終的な理解のまとめ

- HDD / SSD は atomic ではない
- alignment は成功率を上げる工夫でしかない
- torn page は必ず起きる前提で設計する
- redo(WAL) は唯一信じられる情報源
- ページは壊れても OK、redo で踏み潰す
- undo / MVCC は row 単位で別管理するのが自然
- undo は差分ではなく、その時点の row を保持する
